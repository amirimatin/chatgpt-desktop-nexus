# رفع ناسازگاری Claude در OmniRoute برای Codex

این گزارش نتیجه بررسی و اصلاح درگاه `https://om.candocloud.ir/v1` در تاریخ `2026-10-11` است. مشکل در فهرست مدل ها و تبدیل پاسخ در OmniRoute نسخه `3.8.51` بود. برای رفع آن، تصویر کانتینر `omniroute:3.8.51-codex-claude-fix-20261011` ساخته و روی سرور مستقر شد. اجرای واقعی Codex CLI با مدل های Sonnet high و Opus high پس از اصلاح موفق بود.

## چرا Claude Code کار می کرد ولی Codex خطا می داد؟

OmniRoute درخواست های چند ارائه دهنده مدل را دریافت می کند و قالب درخواست و پاسخ را برای هر کلاینت تبدیل می کند. Nexus نشانی درگاه و مدل انتخابی را به Codex می دهد. بنابراین نمایش یک مدل در فهرست Nexus، به تنهایی موفقیت درخواست آن مدل را تضمین نمی کند.

Claude Code از مسیر بومی Anthropic یعنی `/v1/messages` استفاده می کند. Codex درخواست را با قرارداد Responses به `/v1/responses` می فرستد. این دو درخواست در OmniRoute از مسیرهای تبدیل متفاوتی عبور می کنند. آزمون موفق مسیر Messages و شکست بازتولید شده مسیر Responses نشان داد که اتصال Claude برقرار بود، ولی مسیر مورد استفاده Codex ایراد داشت.

## علت های بازتولید شده

### ۱. پسوند سطح تفکر در فهرست مدل ها شناخته نمی شد

درگاه در `/v1/models` مدل هایی مانند `cc/claude-sonnet-5-high` و `cc/claude-opus-5-high` را منتشر می کرد. اما فهرست مرجع وارد شده به OmniRoute، شناسه پایه مدل ها را بدون ویژگی `supportedThinkingEfforts` نگه می داشت. این ویژگی سطح های پشتیبانی شده تلاش برای تفکر را مشخص می کند.

هنگام دریافت درخواست مدل `-high`، بخش تشخیص مدل (`resolver`) برای جدا کردن پسوند سطح تفکر به همین ویژگی نیاز داشت. چون ویژگی موجود نبود، کل نام دارای پسوند را یک مدل مستقل تلقی می کرد. این نام در فهرست مرجع وجود نداشت و درخواست با HTTP 400 رد می شد:

```text
Model 'claude-sonnet-5-high' is not available in the active live catalog for provider 'claude'.
```

افزودن موقت این ویژگی به پایگاه داده SQLite درخواست را درست کرد، اما تازه سازی فهرست آن را دوباره حذف کرد. بنابراین اصلاح نهایی در زمان خواندن فهرست انجام شد تا به تغییر مکرر پایگاه داده وابسته نباشد.

### ۲. پاسخ موفق Responses با قالب اشتباه به جریان تبدیل می شد

در یک درخواست جریانی به `/v1/responses`، حضور ابزار `web_search` باعث می شد OmniRoute درخواست بالادست را بدون جریان ارسال کند؛ حتی اگر مدل از ابزار استفاده نکند. این مسیر جایگزین (`fallback`) یک پاسخ کامل JSON دریافت می کرد و باید آن را به رویدادهای Responses تبدیل می کرد.

تبدیل کننده موجود برای قالب Chat Completions نوشته شده بود و انتظار فیلد `choices` داشت. پاسخ Responses دارای `output` بود. در نتیجه پاسخ موفق بالادست به خطای جریانی تبدیل می شد و متن همان JSON موفق داخل پیام خطا قرار می گرفت. درخواست مشابه بدون `web_search` موفق بود؛ این تفاوت در آزمون مستقیم بازتولید شد.

اصلاح، پاسخ با `object: "response"` و آرایه `output` را در همین مسیر تشخیص می دهد و رویدادهای درست Responses را می سازد. در این حالت رویدادها پس از دریافت پاسخ کامل بالادست تولید می شوند؛ سرعت دریافت آنها نشان دهنده جریان زنده تولید توکن از مدل نیست.

### ۳. جزئیات مصرف توکن برای Codex ناقص بود

پس از اصلاح جریان، اجرای واقعی Codex CLI خطای دیگری را آشکار کرد:

```text
failed to parse ResponseCompleted: missing field cached_tokens
```

برخی پاسخ ها جزئیات مصرف توکن (`usage`) مورد انتظار Codex را نداشتند. Codex پس از اجرای موفق ابزار، رویداد پایان پاسخ را نمی خواند و دوباره تلاش می کرد. این رفتار ممکن بود اجرای ابزار را تکرار کند.

اصلاح نهایی فیلدهای `input_tokens_details.cached_tokens` و `output_tokens_details.reasoning_tokens` را، وقتی غایب باشند، تکمیل می کند. اگر شمارنده معادل موجود باشد از همان استفاده می شود؛ در غیر این صورت مقدار صفر گذاشته می شود. مقدار موجود این فیلدها حفظ می شود.

## اصلاح کد و نحوه اعمال آن

کد سازگاری در `lib/omniroute-responses-compat.js` قرار دارد:

| محل کد | مسئولیت |
| --- | --- |
| `lib/omniroute-responses-compat.js:1`، تابع `createResponsesStreamResponse` | تبدیل پاسخ کامل Responses به رویدادهای جریانی سرور (`Server-Sent Events` یا `SSE`) |
| `lib/omniroute-responses-compat.js:4` | تکمیل جزئیات مصرف توکن و حفظ شمارنده های موجود |
| `lib/omniroute-responses-compat.js:21` | حفظ پیام، خلاصه تفکر، امتناع از پاسخ و فراخوانی ابزار در رویدادها |
| `lib/omniroute-responses-compat.js:64` | حفظ وضعیت نهایی `completed`، `incomplete` یا `failed` |
| `lib/omniroute-responses-compat.js:74`، تابع `enrichClaudeLiveCatalog` | افزودن ویژگی سطح تفکر به مدل های موجود Claude هنگام خواندن فهرست |
| `scripts/patch-omniroute-responses.js:7`، تابع `patchOmniRouteResponsesBundle` | درج تبدیل کننده در فایل کامپایل شده مسیر جایگزین Responses |
| `scripts/patch-omniroute-responses.js:19`، تابع `patchOmniRouteCatalogBundle` | درج تکمیل ویژگی های فهرست پیش از جدا کردن پسوند سطح تفکر |
| `tests/omniroute-responses-compat.test.js` | هشت آزمون سازگاری پاسخ، ابزار، مصرف توکن و فهرست مدل ها |

رویدادها با `response.created` شروع می شوند، خروجی و آرگومان ابزار را منتقل می کنند و با وضعیت واقعی پاسخ پایان می یابند. شناسه ابزار، `call_id`، نام، فضای نام (`namespace`)، آرگومان ها و ورودی ابزار سفارشی حفظ می شوند. پاسخ ناموفق به پاسخ موفق تبدیل نمی شود.

برای فهرست، قابلیت های اعلام شده خود درگاه در `advertised-claude-efforts.json` ذخیره شد. اصلاح در زمان اجرا ویژگی سطح تفکر را برای ۱۱ مدل پایه موجود تکمیل می کند. اگر فهرست مرجع از قبل آرایه `supportedThinkingEfforts` داشته باشد، همان مقدار حفظ می شود. مدل تازه ای به فهرست اضافه نمی شود و درخواست مدل ناموجود همچنان رد می شود.

تصویر نهایی شامل اصلاح فایل جریان و هر شش نسخه منطبق بخش تشخیص مدل در فایل های کامپایل شده است؛ از جمله بخش مشترک HTTP و مسیر داخلی Responses از طریق WebSocket. برای این مشکل تغییر دیگری در رابط Desktop، فایل `app.asar` یا ابزار انتخاب مدل Nexus لازم نبود.

آزمون های CLI با تنظیمات موقت و مستقل انجام شدند. پنجره فعال Desktop کاربر به Claude تغییر داده نشد. بنابراین این شواهد مسیر واقعی اجرای ایجنت CLI را تایید می کنند؛ تایید تعاملی همان پنجره Desktop در این بررسی انجام نشده است.

Codex برای شناسه های سفارشی Claude همچنان هشدار استفاده از ویژگی های پیش فرض مدل می دهد. این هشدار مانع پایان موفق هیچ یک از دو اجرای نهایی نشد.

## استفاده در Desktop

در تنظیمات ارائه دهنده Nexus، نشانی پایه باید `https://om.candocloud.ir/v1` باشد. کلید دسترسی را فقط در محل تنظیمات ارائه دهنده وارد کنید. سپس یکی از مدل های تایید شده، مانند `cc/claude-sonnet-5-high` یا `cc/claude-opus-5-high`، را انتخاب و گزینه `Apply & Reload` را اجرا کنید تا تنظیمات در نشست Desktop بارگذاری شود.

در صورت بازگشت خطا، نام دقیق مدل، مسیر درخواست و رویداد پایان پاسخ را بررسی کنید. نمایش نام مدل در `/v1/models` به تنهایی برای تایید سلامت مسیر Responses کافی نیست.

## آماده سازی اصلاح برای نگهداری

اسکریپت `scripts/patch-omniroute-responses.js` به صورت آفلاین کار می کند: فایل کامپایل شده را دریافت و نسخه اصلاح شده را تولید می کند. ساختار نامنطبق را با خطا رد می کند. این اسکریپت اتصال به درگاه، دریافت کلید یا استقرار انجام نمی دهد.

برای آماده سازی دوباره، فایل های اصلی و اصلاح نشده همان نسخه را ورودی بدهید. جایگزین های زیر نام فایل هستند و باید با مسیر واقعی جایگزین شوند:

```sh
node scripts/patch-omniroute-responses.js INPUT_STREAM_BUNDLE OUTPUT_STREAM_BUNDLE
node scripts/patch-omniroute-responses.js --catalog INPUT_CATALOG_BUNDLE OUTPUT_CATALOG_BUNDLE ADVERTISED_EFFORTS_JSON
npm test
```

اسکریپت وجود نشانگرهای `nexus-responses-fallback-v1` و `nexus-claude-catalog-v1` را بررسی می کند. اگر نشانگر وجود داشته باشد، فایل را بدون تغییر برمی گرداند. پس برای تغییر محتوای اصلاح، استفاده از خروجی اصلاح قبلی به عنوان ورودی کافی نیست.

این اصلاح به ساختار کامپایل شده OmniRoute `3.8.51` وابسته است. هنگام ارتقا، باید اصلاح معادل در نسخه اصلی موجود باشد یا اصلاح برای نسخه جدید بازسازی و آزموده شود. جایگزینی تصویر سفارشی با تصویر اصلاح نشده، تغییرات این گزارش را حذف می کند.

## بازگردانی سرویس

دستورهای زیر صرفا روش بازگردانی هستند و در ثبت این مستند اجرا نشده اند. این کار تنظیمات اولیه را برمی گرداند و کانتینر را با تصویر اولیه نگه داشته شده دوباره ایجاد می کند:

```sh
cd /core/compose/services/omni-router
cp docker-compose.yml.backup-20261010-claude-responses docker-compose.yml
docker compose up -d --no-deps --pull never omniroute
```

پس از بازگردانی، وضعیت سرویس و مسیرهای `/v1/messages` و `/v1/responses` باید دوباره بررسی شوند. مشکلات سازگاری گزارش شده ممکن است با بازگشت تصویر اولیه دوباره ظاهر شوند.

تغییر موقت SQLite با اصلاح زمان اجرا جایگزین شده است. فهرست خام در تایید نهایی همان شناسه های پایه را داشت و ویژگی سطح تفکر افزوده شده ای در آن باقی نمانده بود. استقرار نهایی به ویرایش دوره ای یا بازگردانی SQLite وابسته نیست.
